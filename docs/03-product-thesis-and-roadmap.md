# 产品定位与路线：人机共驾的采集工作台

2026-10-15。目标从「给 agent-browser 做个中继」改为**自用、开源的采集与协议分析工具**。背景见 `01`。

标注：【实测】跑过；【推断】间接推出；【待验】没验证。

## 1. 一句话

程序员和 AI **共用同一个真实的 Chrome**（默认是工具自己管的工作副本，登录态由 `store` 加 AI 登录建立；也能接管你自己的 Chrome）：AI 探路、放大，卡住或拿不准就交还给人，人给凭据、过验证、核结论；全程录下证据，每个结论都能回放验证。

## 2. 为什么市面上的工具不好用

现有工具大多从「给 agent 一个单独的纯净浏览器，让它全程自己跑」出发。真实的采集工作不是这样：

- **第一次接触目标，一定要先登录、把页面和流程走一遍**，搞清楚数据在哪、流程怎么走，才开始写代码。探路可以由 AI 做，但登录态要留得住、过程要被记下来、人要能随时在同一个窗口里插手；一次性的纯净浏览器三样都没有。
- **AI 跑到一半必然会卡**：验证码、二次验证、风控页、页面和预期不一样、找不到元素。这时候需要人在同一个页面上帮它过验证、看一眼页面再交回去。另开的浏览器人插不进手。
- **结论要人来确认**：「目标接口是这个、这个参数是签名」这种判断，得人在页面上核一眼。

市面上为什么不这么做【推断】：
1. 做 agent 浏览器的多是云浏览器和基础设施公司，隔离的纯净浏览器好扩容、好卖。
2. 「AI 全自动」的演示好看。
3. 驱动用户的真实浏览器要么走远程调试端口（弹框、抢焦点），要么做扩展（难开发、难分发）；安全上也更敏感，厂商宁可回避。
4. 少数能接真实浏览器的（Kimi、Playwright MCP Bridge 等）是为「替人做操作」设计的，不是为抓包和协议分析设计的。

## 3. 核心工作流（产品按这个来设计）

| 步骤 | 谁 | 工具做什么 |
|---|---|---|
| 1. 探路 | AI（人给凭据） | 作者把登录信息交给工具（凭据不进模型，§10 第 7 条），AI 开后台标签自己登录、点页面；工具全程录制：请求、响应、操作时间线、截图。撞到验证码、二次验证、需要人点的地方停下，在终端和浏览器喊人。AI 的探索就是第一份证据包 |
| 2. 定位 | AI | 在证据包里反查目标数据在哪个接口、参数怎么分类、值从哪个前序响应来、由哪段 JS 发出 |
| 3. 确认 | 人 | AI 把结论和证据摆出来（高亮页面元素、列出候选接口），人确认或纠正；确认结果写进证据 |
| 4. 放大 | AI | 在同一会话里按探路走过的流程换参数多录几遍，补齐分页、边界情况 |
| 5. 卡点交还 | AI → 人 → AI | 遇到验证、风控、异常或拿不准，AI 停下，在浏览器和终端提示人；人处理完点继续 |
| 6. 复现 | AI | 生成独立客户端，重放请求，与录到的响应逐项比对 |
| 7. 落地 | AI + 人 | 导出离线 fixture 和测试；回归多份样本；定时重放，检测接口变化 |

人可以随时接管：工具发现人正在操作 AI 的标签，AI 就暂停【待验：能否可靠识别】。

## 4. 这个工具体现的工作方式

来自一线采集工作的经验，写成工具行为，不靠自觉：

- **证据分级**：每条结论标【实测】/【推断】/【待验】。参数来源、根因这类判断，必须有重放或实验坐实才算【实测】。
- **AI 提议，确定性工具验证**：能用搜索、diff、重放解决的，不让模型猜。
- **离线回放优先**：能用录下的证据回放，就不去打真实网站。
- **账号保护是一等功能**：实际使用的常是真实在用的账号，打多了会被风控（登录正常、取数返回空），影响账号主人。工具内置限量与熔断（§5 guard）。
- **结果为空先怀疑查询**：`find` 搜不到时，先检查响应体是不是压缩、编码或加密了，而不是直接下「接口里没有」的结论。
- **期望产物先行**：先写出期望的输出（golden）再写规则，测试能自动跑、提交前能强制执行。
- **证据要新**：代码改了，旧证据作废；验证必须是同一路径重跑。
- **会话会过期**：验证要覆盖「缓存会话已过期」的场景，不能只用刚登录的会话。

## 6. 不做什么

- 不做无人值守的全自动采集平台，不做云浏览器。
- 商业反爬防护（JSVMP 类）：
  - **做**（黑盒录制）：把挑战原样录成样本包（§5 `sample`），供用户或独立项目（作者自己的离线分析项目）离线分析。工具只是忠实录音。
  - **不做**：脱机客户端、脱虚拟化、还原/抽取签名算法、伪造请求、伪造环境过验证、白盒插桩保护运行时内部。这些若有，归作者自己的离线分析项目，且是用户自己的研究，不在本工具范围。
  - 这类站点的采集留在真实浏览器会话里，挑战由人处理（§3 步骤 5）。
  - 工具不带任何验证码或挑战的解法；用户可以自己写处理程序放进 `~/.config/tabcap/plugins/`、用 `tabcap plugin enable` 加载（`04` §18），处理程序怎么处理挑战由用户自己决定，不在本工具范围。
- 作者自己的离线分析项目与本项目无关，本项目只负责**采到供它用的素材**，不替它分析。
- 主仓库不放针对具体网站的破解模块和签名算法。
- 定位是「分析和调试你自己的会话」。

## 7. 路线

每个阶段先写验收标准（能自动跑的就写成测试），做完按标准验收。

### 阶段 1：共用浏览器 + 录制 + 反查（自用就见效）

- `bridge` 最小版：`setup`（下载 Chrome for Testing、建 profile、自动装 UI 扩展）、`browser start/stop`、`direct` 传输层；工具集参照常见 agent 浏览器（navigate、snapshot、click、fill、evaluate、screenshot、标签与会话管理）。`--executable-path` 可指向已装的 Chrome 二进制加独立 profile（此时 UI 扩展装不上，退回手动）。
- `capture` + `bundle`：AI 操作的主动录制；人介入时刻的录制（截图与导航，操作级录制在阶段 2）。
- `analyze find`、`analyze diff`。
- 命令行 + skill。
- `handoff` 最小版：AI 撞上验证码、风控或拿不准就停下，在终端说明原因并给截图路径，人处理完说「继续」。协议化状态机、浏览器侧按钮、人接管识别在阶段 2。
- `guard` 最小版：每站点每会话登录尝试 1 次，再试要显式确认；响应出现 403 / 429 或验证页特征就停下交人。预算、熔断、探测模式在阶段 2。
- `store` 最小版：`site add`（密码交互输入或 stdin）、`session start --site`、`fill --secret 站点.password`、守护进程输出替换。登录配方与会话复用在阶段 2。

验收：
1. `bbl setup` 一条命令从零到可用，全程不点任何对话框、不进 `chrome://extensions`；连续使用一天不出现任何授权弹框；用户在别的应用里打字时，AI 操作不把浏览器拉到前台。
2. AI 用凭据登录并走一个跨多页的流程，事后证据包里每个 XHR / fetch 的响应体都在，包括跳转前的页面发出的请求；凭据明文不出现在模型输入、日志和 CLI 输出里。
3. 拿页面上看到的一段文字执行 `find`，命中返回它的接口；响应体是 gzip / br / base64 时也能命中；搜不到时提示可能加密。
4. 同一流程换参数录两次，`diff` 正确分出常量、会话值、时间戳和变化值。
5. 本地靶场（§10 第 5 条）的阶段 1 场景全部通过，能一条命令自动跑。
6. AI 在靶场撞上验证页时停下并在终端提示，人处理后继续，之后的请求齐全；同一会话第二次登录尝试被拦下要求确认。

### 阶段 2：人在回路 + 账号保护 + 复现

- `handoff` 完整版：协议化状态机、浏览器侧提示与按钮、确认题、人接管时 AI 暂停、人介入时刻的操作级录制。
- `guard` 完整版：预算、熔断、探测模式。
- `store` 完整版：登录配方（`login <站点>` 一条命令重登）、最近会话 cookie 复用与过期检测、证据包索引；`replay` 和 `watch` 先用旧会话，过期才重登，重登受 guard 限次。
- `bridge` 的 `ext` 传输层：扩展挂 `chrome.debugger` 接管用户自己的 Chrome；扩展上 Chrome Web Store（unlisted）供一键安装。
- `analyze deps`、`analyze trace`。
- `replay`：生成客户端 + 逐项比对；离线回放服务器。

### 阶段 3：维护与扩展

- `watch` 漂移告警、多样本回归。
- 插件：hook 套件、反混淆、作者自己的 JS 分析研究项目、线路层（TLS / h2 指纹）诊断外部工具。
- MCP 接口；CDP 兼容端点（`07` §2），让 Playwright / DrissionPage 等也能接；考虑支持 Firefox（扩展没有 `chrome.debugger`，要走 WebDriver BiDi，另行调研）。

## 8. 决策

已定（2026-10-15）：
- **技术栈**：扩展、守护进程、命令行全用 TypeScript，运行时 Bun（Bun 专有 API 可用，反正要编译打包）；生成的复现客户端用 Python。以后真需要原生组件，用 Rust 或 Zig，不用 Go。
- **许可证**：Apache-2.0。要抄的代码（Playwright `cdpRelay.ts`、agent-browser-stealth）都是 Apache-2.0；DrissionPage 是自定义非商业许可，只借思路。
- **调试横幅**：接受。会话期间一直录。
- **提示渠道**：终端和浏览器同时提示，不发系统通知。
- **探路由 AI 做**：人给凭据，人只在验证码、二次验证、需要人点的时刻介入（§3、§10 第 7 条）。
- **AI 分工**：本目录另立 `AGENTS.md`：AI 可写任何模块、作者审；expected 只来自 oracle。
- **架构**：薄扩展、厚守护进程（`07` §1）；CDP 兼容端点放阶段 3（`07` §2）。
- **产品形态**：CLI 是 AI 的手和笔记本；扩展只做人的那一面（状态条、继续 / 接管 / 停止、待答问题），不放模型；MCP 阶段 3。
- **浏览器**：两条传输层都做，`direct` 默认且先做：`setup` 下载 Chrome for Testing（Chrome 137+ 品牌版不再认 `--load-extension`【实测：Chromium Extensions 公告】），独立 profile，直连 CDP，macOS 加 `--use-mock-keychain` 避开钥匙串弹窗（【实测】spike 1）；默认跟随系统代理、可用 `--proxy` 切换；Chrome 后台外连用 Playwright 的默认参数表压到最少；`ext` 阶段 2，扩展届时上 Chrome Web Store（unlisted）。
- **第一步**：按阶段 1 做；写代码前先做 `06` §6 的两个 spike。
- **不接 Integuru，自研 `deps`**（10-15 作者定，推翻同日早些的「接外部引擎」）：本项目的作用类似采集与集成的开发框架，流程为 录制 → 分析 → 回放 / 生成脚手架 → 交还调用方的主 agent 填空并用 `replay check` 验证 → 维护。不做 agent、不依赖任何模型；`deps` 是确定性的值流依赖图（算不出的标 `computed-in-page`，不猜）、`analyze chain` 给出动作链、`export-python` 按动作链出带 TODO 和 `verify()` 的脚手架。放 0.4，与 `where` 的值归一化一起做。Integuru 不接：AGPL-3.0、Poetry、只认 OpenAI。

- **名字**：`tabcap`（10-15 作者定，抓包工具命名传统：tab + capture）。守护进程 `tabcapd`，环境变量 `TABCAP_HOME`，目录 `~/.config/tabcap`。0.2 起用新名，`bbl` 只在 0.1.0 里出现过。仓库随改名独立建仓。
- **命令壳不换语言**（10-15 作者定，推翻同日早些的「换 Zig」）：壳保持 TypeScript。理由：Bun 编译的壳启动 13.5 ms【实测】，省不出可感知的延迟；守护进程仍是 Bun，包体不变；学习这条理由在改由 Opus 写之后不成立。只做最小的 schema 契约：`tabcap schema --json` 从命令注册表导出，SKILL.md 与 README 的命令表由它生成并在测试里断言一致；socket 上的 `GET /schema` 等阶段 3 做 MCP 时再开，MCP 工具表直接由 schema 转换。
- **爬虫的闭环**（0.6-A，10-16 作者定，来自作者真实项目里 v0.5.0 的试用：只录人的浏览只覆盖了爬虫 20 个请求里的 7 个）：录制 → 爬虫的请求经已登录的标签发出并录下（`tabcap fetch` / `POST /fetch`）→ 导出 HAR / 夹具 → 离线回放。
- **浏览器过关、脚本跑量**（10-16 作者定，0.6-F）：登录、验证、需要人点的那一步留在浏览器里（人在回路，§3）；过了之后 `tabcap session export --for requests|httpx` 把标签的 cookie、页面真正发的认证头（`Authorization`、`access-token`、`x-csrf` …）和 localStorage / sessionStorage 里的 token 交给脚本（0600 文件，值不打印，`04` §8.2），批量请求由脚本自己发；少量、必须带浏览器上下文的请求仍走浏览器（0.6-A `fetch`）。全程 `net start` 录着，脚本拿到的头来自哪条录下的请求在输出里写明（`source.headers`）。会话过期就回浏览器重新过关、再导一次。
- **回放的匹配键可配**（0.6-C，10-16 作者定，来自同一次试用：离线回放三个站点要手写三种规则，加密正文的站点 `replay serve` 一条都配不上）：一份规则文件 `tabcap-replay-rules/0`（也可放 config.json 的 `replay` / `sites.<名>.replay`），`replay serve`、`replay check`、`bundle export fixtures` 共用；默认规则就是原来的行为；夹具格式可插拔（夹具插件），项目里手写的离线回放脚本可以删掉（`04` §31）。
- **原生化的第一个组件是 `analyze`**，不是壳：Zig 导出 C ABI，经 `bun:ffi` 接入；触发条件是实测 `find` 或 `diff` 在真实包上超过 2 s，或 `deps` 落地时。触发前先把 TS 版和夹具做扎实，TS 版加夹具就是原生版的 oracle。

待定：
1. **仓库边界**：仓库只放本项目自己的代码、靶场与合成数据；不出现任何真实站点的数据、账号或第三方专有材料。

## 9. 风险

- **范围太大**：一个人维护，模块多了会摊薄。先把阶段 1 做到自己离不开。
- **平台变化**：Chrome 收紧 debugger 或 MV3 规则、官方 DevTools MCP 往这边长。价值放在证据格式、分析和人在回路流程上，连接层做成可替换。
- **同质化**：「AI 分析签名」的 MCP 已经很多（见 `01` §4 与当时的检索），不在这条线上硬拼，能集成就集成。
- **合规与名声**：守住 §6，项目才不会被下架或被看成黑产工具。

## 10. 关键设计判断（10-15 讨论）

1. **证据包先定规范**：清单文件 + 事件流（请求、操作、交接、确认，一行一条）+ 按内容哈希去重的正文 + 截图。能导出也能导入 HAR，DevTools / Charles / mitmproxy 的包也能用分析命令。先写规范和期望样例，再写代码。
2. **人机交接当协议设计**：状态分 AI 在跑 / 等人（原因 + 问题）/ 人在操作 / 恢复，两边都能切换；AI 侧 `handoff ask` 阻塞等答复（带超时）；确认题答案记为【人确认】。识别人接管：CDP 发的输入在页面上也是 `isTrusted=true`，靠守护进程记录自己发输入的时间窗来区分【推断，待验】。
3. **默认最少打扰**：插桩会改变页面行为，影响证据真实性，也可能连累真实账号。默认只开 Network 与 Page；需要调用栈或动态代码时，显式进入追踪模式并提前告诉人。
4. **录包要过的硬骨头**：正文在请求完成时立刻取并加大缓冲，再对 XHR / Fetch / Document 三类默认开 `Fetch` 拦截补齐跳转竞态（【实测】spike 2，`04` §5.2 第 8 条）；取不到写明原因（重定向、304、导航取消、流式）；Service Worker、跨源 iframe、页面弹出的新窗口要自动挂上并归进同一份证据【实测 10-15 spike 1：`direct` 模式下跨源 iframe 与 Service Worker 经 `Target.setAutoAttach {flatten:true}` 自动挂上，子会话各自收到自己的 Network 事件；弹窗也挂上，前提是守护进程对每个挂上的会话发 `Runtime.runIfWaitingForDebugger`（`07` §1.1）；`ext` 模式的 `chrome.debugger` 支持阶段 2 再验】；应用层加密的响应，在追踪模式下记录页面解析后的明文；protobuf 等二进制做无 schema 解码。
5. **本地靶场先行**：一组本地小网站，每个演示一种通用模式（token 链、签名参数、加密响应、SPA 跳转、弹窗登录、WebSocket、Service Worker、跨源 iframe、模拟验证页）。同时用作端到端测试、演示和合规的验证对象；不拿第三方网站做测试。
6. **给 AI 的接口**：命令少、统一 JSON、输出有界（大正文只回路径和摘要）、报错写下一步、id 稳定；命令行优先，MCP 后补。页面内容一律标为不可信数据；提交、支付、删除这类写操作默认要人确认。
7. **探路由 AI 做，凭据不进模型**：作者把站点入口、账号、密码录进工具的本地库（§5 `store`），AI 的命令只写引用（`fill <ref> --secret 站点.password`），守护进程取值填入页面，并把所有 CLI 输出、日志、快照里出现的已知秘密值替换成 `<secret:…>`，AI 即使故意用 `evaluate` 读密码框也只拿到占位符；账号名不打码。登录配方和最近会话 cookie 也在库里，重放与 `watch` 先用旧会话，过期才重登。AI 撞上验证码、风控或拿不准就停下交人；「停下 + 终端说明 + 截图」和「登录只试一次、见验证页就停」从阶段 1 就要有（`06` A2.8、A6）。
8. **挑战样本包是证据包的 profile**（`04` §4.3）：`sample` 模式下脚本正文不设上限、多取环境与 cookie 快照、生成 `manifest.sample` 索引。工具只录不析；对保护脚本的分析是作者自己的研究（如作者自己的离线分析项目），拿这份样本离线做。
9. **产品形态**：CLI 是 AI 的手和笔记本，证据包、Python 客户端、fixture 和测试都住在仓库里，AI 在终端才用得上；扩展只做人的那一面（状态条、继续 / 接管 / 停止、待答问题卡片），永远不放模型。分发就是三样：Bun 编译的单文件（守护进程 + CLI）、一个很少更新的扩展、一份 skill。
10. **连接层可替换，专属浏览器优先**：`direct` 模式自己启动 Chrome for Testing，独立 profile，直连 CDP，`Target.setAutoAttach` 原生可用，不需要扩展管道，也避开了 `chrome.debugger` 的 sessionId 支持、单控制者、与其它扩展抢标签这些未知数；`ext` 模式接管用户自己的 Chrome。两者共用守护进程里的会话、焦点阶梯、对话框锁、录制器。人那一面的 UI 是同一个扩展，`direct` 下由 `--load-extension` 自动装，`ext` 下从 Chrome Web Store 装；manifest 固定 `key` 让扩展 id 在两种装法下一致，守护进程按 id 做来源校验。Chrome for Testing 版本固定不自动更新，由我们定期升；它与正式版的指纹是否完全一致【待验】。
